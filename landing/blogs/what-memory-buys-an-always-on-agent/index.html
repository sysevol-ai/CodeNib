What Memory Buys an Always-On Agent

We replayed 76 merged pull requests from five repositories through an always-on review agent, with memory and without. Remembering what it had read and said halved the cost and cut its drafts by 59%. It also raised 22% fewer of the points reviewers went on to make, and reviewing more often did not win them back.

An always-on agent is asleep most of the time. Anthropic's guide Building always-on agents describes what surrounds its loop: an inbox of events, timers, memory, permissions and an outbox. Each time it wakes, it has to work out what it is looking at again, and what it should say. What it pays for that, in tokens and in messages to people, decides whether anyone leaves it on.

We built those parts for GitHub issues and pull requests as codenib threads agent, and then measured what its memory is worth. Replayed over the life of 76 merged pull requests, against the same agent with no memory, it cost 0.52× as much and filed 0.41× as many drafts. It raised 0.78× as many of the points the human reviewers later made.

An agent that sleeps between passes

The agent runs as a pass, every 15 minutes from cron. A pass fetches what changed on the issues and pull requests it follows. Code, not a model, then decides whether the news asks for a response: a label, a passing check, a bot comment or a merge does not. Only when something does is Claude Code woken, with read-only tools in a clone of the repository. Whatever it concludes, a reply, a question or nothing, is filed for a maintainer, and only then is the news marked read.

The parts of an always-on agent and how codenib threads agent provides each
PartIn codenib threads agent
Event inboxEach thread is a stored list of events. A run claims the news under a lease and marks it read only when it is done, so a run that fails gets the same news again.
TimersThe agent can ask to be woken in a number of hours, for example to see whether CI passed. A maintainer's answer to its question wakes it too.
MemoryA note per thread that the agent rewrites each run, the maintainers' standing instructions, and what it already said on the thread.
PermissionsRead, search and list files in the clone and the saved diff. No shell, no writes, no network, and never the GitHub token.
OutboxAt most one waiting draft per thread. Nothing reaches GitHub until a maintainer sends it.

Memory is the part this post measures. On every wake after the first, the agent is handed its own note on the thread, the last things it said there, and only what changed since. The alternative is the agent most people would write first: wake it, give it the whole thread, and let it work everything out again.

Replaying a pull request from open to merge

To measure that without posting anything, we replayed history. A pull request is replayed from the moment it opened to its merge, one pass per 15 minutes of its life. Before each pass the agent's store holds only the events that existed by then. The code it reads is a snapshot of the pull request's base with no history, and the diff it sees is the diff of the head at that time. No later commit, review or merge can leak in.

The pull requests are 76 merged ones from five repositories: astral-sh/ruff (36), and ten each from pandas-dev/pandas, prometheus/prometheus, vitejs/vite and tokio-rs/tokio. Every one had an inline review from someone other than its author. Two agents ran each replay with Claude Sonnet 5.5 and the same tools, instructions and wakes:

  • The CodeNib agent, as shipped.
  • A stateless agent, woken by the same news, that reads the whole prepared thread every time and keeps no notes. Its context is CodeNib's own budgeted document, so the comparison leaves out what preparing the thread saves.

Two numbers are simple: what the runs cost, and how many drafts each agent filed for a maintainer. The third asks whether a draft helped. For each point a human reviewer made, a judge model decides, without knowing which agent wrote the drafts, whether an earlier draft had raised the same point. Naming the same file is not enough. Judged twice, the same pairs got the same verdict 140 times in 142.

Half the cost, two drafts in five

With memory, the 76 pull requests cost $11.08 against $21.52, about 15 cents per pull request over its whole life against 28. The agent filed 102 drafts against 249. The two savings have different causes.

It rereads less code

The obvious saving is the thread: a stateless agent is sent the whole thread again on every wake. That turns out to be the small part. On the same later wakes in ruff, our prompt was about 1,200 tokens against 2,300. The agent's own input, its tool calls included, was 9,000 tokens against 24,600, and it took 2.2 turns against 3.3. An agent that knows nothing on waking opens the diff and the code again to rebuild what it knew. A note that says what was asked, what was checked and what is left saves that rereading.

It says things once

The stateless agent wrote a new review on 31% of the later wakes in ruff, the CodeNib agent on 4%. Without a record of what it had said, a new commit or comment looks like a pull request it has not reviewed. In ruff, 11 of the 36 pull requests got three or more drafts from the stateless agent, and one got that many from the CodeNib agent.

Code decides when to wake

Across all five repositories, 42% of the passes in which something changed had nothing that asked for a response: labels, review requests, passing checks, bot comments, a merge. Those passes are read by code and wake no model. The share ranged from 27% in vite to 57% in tokio, and was 30% in ruff. There we also ran an agent woken by any change at all, the simplest loop to write. The CodeNib agent cost 0.37× as much as that one, and filed 0.27× as many drafts.

What memory costs

The CodeNib agent raised 36.5 of the reviewers' points first, against 47 for the stateless agent: 0.78×, with a 95% interval of 0.60 to 0.97. That is a real loss, and it holds per draft the other way round: each CodeNib draft carried 0.36 of a reviewer's points, each stateless draft 0.19. The gap is not spread evenly. Most of it is in pandas, and most of it is one kind of point.

The points come from the first run of each agent and were sorted into kinds by a model. Six in ten are about design and idiom: where code belongs, which existing helper to use, what a simpler form would be. Those are a maintainer's judgment about the project, and both agents raised few of them. The stateless agent's lead is mostly design points. In pandas, half of its extra points came from its third to fifth review of the same pull request, and the other half from first reviews that happened to differ.

Two fixes that did not help

Before reading too much into any one count, we ran the same agent twice. On the four newer repositories it raised 24 points the first time and 21 the second. On 32 ruff pull requests from November it raised 12 and then 10. A difference of a few points between two variants is within that spread.

Reviewing new commits on their own. If the CodeNib agent stays quiet after its first review, perhaps it should review each new push. We gave it the diff of the new commits alone and asked it to review them like the first version. On the 32 November ruff pull requests, which we had not used before, it cost 29% more and filed 50 drafts against 42. It raised 10 points first against 12. The same agent without the rule had also raised 10 on its second run. The rule bought more drafts and nothing else, and we did not ship it.

Wider instructions. Since most points are design and idiom, we told the agent to look for both: search for an existing helper the new code duplicates, check where similar code and tests live. On the four newer repositories, each run twice, it raised 1.5 points more, with an interval of −6.5 to +10.0, at the same cost. Telling the agent what reviewers care about did not change what it found.

Coverage comes from samples

What the stateless agent does differently is review the same pull request again and again. Each review is a sample of what the model might notice, and the samples differ. On 25 pull requests none of the earlier replays had used, we gave the first look's exact input to four independent reviews. One review raised 10.25 of 43 reviewer points on average, any of two 13.7, any of four 18.0.

A stateless agent collects those samples by posting each one. The alternative is to take them all at the first look and merge them. Three reviews merged into one draft raised 13 points, of the 17 the three found between them, in a draft 14% longer than a single review. That is 2.75 points more than one review, with an interval of −0.5 to +6.5: a direction, not yet a result. The first look then costs about four times as much, roughly what memory saves over the life of a pull request.

What we take from it

  • Decide wakes in code. Four passes in ten had nothing to respond to. A model should only see news that asks something of it.
  • Give the agent its notes and its own words. Without them it rereads the code on every wake and says the same thing again. With them it costs half as much and files fewer than half the drafts.
  • Treat each review as a sample. Reviewing more often finds more, one message at a time. Several reviews at the first look, merged, may find the same in one message.
  • Replay before you ship. History replayed without leaks, a judge blind to the variant, and every variant run twice. Two of our three ideas looked good until they were measured.

Try it

codenib threads agent ships in the next CodeNib release. It needs Git, Claude Code, and a GitHub token in GH_TOKEN or a signed-in gh. Run it inside a clone, from cron every 15 minutes:

codenib threads agent run --watch pulls   # one pass: poll, wake the agent where needed
codenib threads agent outbox              # the drafts and questions waiting for you
codenib threads agent send ID             # post one draft as a comment
codenib threads agent status              # tickets, follow-ups and what the runs cost

The agent drafts and a maintainer sends, so nothing reaches GitHub on its own. On CodeNib's own repository its first pass ran once on each of the four open pull requests, for $0.20 in all, and a pass with nothing new made nine GitHub requests and no model call. Every command and option is in the thread guide.

Replays ran with Claude Sonnet 5.5 through Claude Code, one pass per 15 minutes from opening to merge, and nothing was posted. Pull requests were merged between October 1 and November 18, 2026, changed at most 30 files and 1,500 lines, were open at most 14 days, and had an inline review from someone other than the author. Only those never force-pushed, stacked or rebased were kept, so the replay knows what each one held at every moment; that leaves out teams that rebase as they review. Costs are as Claude Code reported them. The judge is the same model, and a point counts as raised if an earlier draft made it, whether or not a maintainer would have sent that draft. The reviewers' points are what they chose to write, so a correct point no reviewer made scores nothing. The per pull request rows, the summary, the selection rules and the script to reproduce them are in the thread guide.
