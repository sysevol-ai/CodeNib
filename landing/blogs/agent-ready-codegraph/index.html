Agent-ready CodeGraph: from checkout to source-linked context

Search finds where to look. CodeGraph shows what the code touches—and links that structure back to the source lines behind those relationships.

Coding agents often struggle when they start with the wrong context: a similarly named function, an incomplete dependency chain, or a source window from a different revision. CodeNib’s agent-ready CodeGraph is designed to make that first read both structural and verifiable.

The default path is deliberately local and model-free. It combines ranked BM25 retrieval with a static, source-linked symbol graph produced by supported SCIP or clangd providers. The graph supplies definitions, references, and dependency neighborhoods where the selected language provider supports them; bounded source reads supply the evidence. No embedding model or API key is required for this path.

A graph that terminates in source

A useful repository graph is not an architecture sketch generated from prose. It is a navigation layer whose nodes and relationships can take the reader back to code. CodeNib keeps the containment structure—repository, directory, file, symbol—separate from the reference overlay between symbols. That makes a large repository readable without flattening it into a hairball.

When an anchored relationship is available, its source location travels with it. A relationship can open its source use site; a symbol can open its definition; a focused dependency view can stay within an explicit depth and output budget. The graph does not replace reading code. It selects the code that deserves to be read next.

One command, four contracts

codenib codegraph init /absolute/path/to/repository
01 / INSPECT

Detect the repository

Identify graph-capable languages, available toolchains, and installed Codex or Claude Code clients.

02 / COMPILE

Build coordinated views

Materialize BM25 and symbol_graph outside the target checkout under one manifest.

03 / CONNECT

Register through native CLIs

Ask each detected agent to own its stdio MCP configuration instead of editing client files directly.

04 / VERIFY

Bind context to source

Record managed client ownership, then verify the manifest against the live source before the server reports ready.

Running the command again is idempotent when the index and managed registrations still match. Different checkouts receive different server names, so an agent can work across several repositories without sharing ambiguous state. Codex receives a user-level registration; Claude Code receives a repository-local registration. The native client configuration changes, while the target checkout remains unchanged.

What the agent receives

The MCP surface keeps retrieval, graph navigation, and source access distinct. That separation makes a tool call inspectable and lets the agent spend a bounded context budget where it matters.

explore_context

Composes ranked retrieval, symbol routing, dependency expansion, and verified source windows for a repository question.

dependency_subgraph

Returns a bounded caller, callee, or impact neighborhood around a resolved symbol.

search_bm25

Finds exact identifiers and lexical matches without requiring a model.

lsp_definition / lsp_references

Navigates static definition and reference signals backed by the graph or a verified live provider.

read_source

Reads an exact, repository-contained 1-based source window after retrieval or navigation.

A good first instruction to an agent is concrete about both the tool and the evidence standard:

Use CodeNib's explore_context to explain where request retries are implemented. Cite the returned source paths and lines before proposing an edit.

For a change-impact question, switch from discovery to structure:

Use dependency_subgraph on RetryPolicy.execute with direction impact and depth 2. Summarize the callers that could change if its behavior changes.

Fail closed beats confidently stale

Repository context is only useful when its provenance is clear. CodeGraph initialization therefore requires a clean Git working tree and checks it again after indexing and client registration. The reusable index lives outside the target checkout. CodeNib may install package-managed graph providers, but it does not run a repository package manager, invoke sudo, or synthesize project prerequisites behind the user’s back.

At server startup, the indexed source identity is checked against the live checkout. A changed repository is not silently served with an old graph. Rerun init after source changes: a completely current view can be reused, while changed source takes the safe rebuild path instead of publishing partial state.

codenib codegraph status /absolute/path/to/repository --json
codenib codegraph init /absolute/path/to/repository
codenib codegraph uninstall /absolute/path/to/repository

status exposes the readiness contract to both humans and automation. uninstall removes only receipt-owned client registrations and leaves the reusable index intact. If a managed client command has drifted, CodeNib stops and asks the user to inspect it rather than guessing.

The same structure has a human view

The browser Dependency Map uses the same symbol graph as the agent tools. Its Structure view expands directories, files, and symbols while rolling relationships up to the nearest visible ancestors. Its Graph view opens file scopes into concrete symbols, preserves edge source anchors, and lets a reader jump from a relationship to code.

This is the larger idea behind CodeNib: build repository context once per indexed source identity, then let humans and agents inspect different projections of the same source-linked artifact.

Try the 0.2.1 preview

The preview requires Python 3.10+, Git, an installed Codex or Claude Code CLI, and a clean target checkout. Clone CodeNib, install the graph and MCP extras from source, then point the initializer at an absolute repository path:

git clone https://github.com/sysevol-ai/CodeNib.git
cd CodeNib
python -m pip install -e ".[graph,mcp]"
codenib codegraph init /absolute/path/to/repository --dry-run
codenib codegraph init /absolute/path/to/repository

Language providers have different system and project prerequisites. CodeNib reports those boundaries before it publishes an incomplete agent setup; the language capability matrix records the current coverage.
