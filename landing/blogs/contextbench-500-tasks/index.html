CodeNib on ContextBench: 388 of 500 Issues Resolved

A complementary search pair, source on demand, and a repair agent—evaluated together on 500 repository issues across eight languages.

A coding agent needs to find the right code and turn that understanding into a working fix. In our ContextBench run, CodeNib resolved 388 of 500 tasks, with 77.90% line recall and an average of $0.68 in recorded model usage per task, including unsuccessful attempts.

A fix and the code behind it

ContextBench evaluates how coding agents find and use repository context while resolving issues. Alongside the final patch, it scores overlap with human-annotated relevant code at file, block and line levels. That makes it possible to ask two separate questions: did the fix satisfy the task's test criteria, and how much of the relevant implementation did the agent find?

Our submission uses the 500-task verified split. It contains tasks from SWE-Bench-Verified, SWE-Bench-Pro, SWE-PolyBench and Multi-SWE-Bench, covering C, C++, Go, Java, JavaScript, Python, Rust and TypeScript. The larger ContextBench dataset contains 1,136 tasks; the numbers in this article describe only our submitted 500.

Native Pass@1 is the fraction of attempts whose final patch passed the pinned task-specific grading criteria. It does not mean every test in each repository passed. Line recall measures how much annotated relevant code appears in the selected source context; precision measures how much selected code overlaps those annotations. F1 balances the two, calculated per task and then averaged.

Search broadly, carry locations, read on demand

The core design is to pass source locations between models and fetch the actual code when the next model needs it. A compact handoff can point to a relevant implementation without filling the repair agent's initial context with every search result.

  1. Find an initial path

    A Haiku worker reads the issue and searches the pinned repository with CodeNib's file discovery, grep and source-reading tools.

  2. Look for what the first search missed

    A second Haiku worker receives the issue and bounded navigation metadata from the first worker. In its own context window, it inspects complementary entry points, callers, tests and configuration.

  3. Hand over locations, then repair

    CodeNib combines the observed ranges into at most 2,048 tokens of navigation metadata, with source identity and explicit omissions. Opus uses source-reading tools to inspect the code it needs, then edits and runs self-tests through the mini SWE-agent container shell.

  4. Grade the patch and account for the reads

    The native evaluator grades the unchanged final candidate patch. CodeNib assembles selected context from search observations and confirmed reads of the original source, and includes model usage from every attempt.

The 2,048-token limit applies to the initial navigation, rather than all later source reads. Source locations bind to a repository version, so the receiving agent can request the intended code. For evaluation, a location or generated summary alone earns no source-read credit: the source must appear in a confirmed model input.

This run evaluates that complete agent and model combination. Embeddings, Jev reranking and graph expansion were outside the measured route. The result therefore does not establish an isolated gain from any of those CodeNib capabilities.

388 resolved, with all 500 attempts counted

The overall resolution rate is 77.60%. The source groups show where the outcome varies: 152 of 174 SWE-Bench-Verified tasks were resolved, compared with 34 of 54 SWE-Bench-Pro tasks. These groups have different repository, language and grading compositions; their differences describe this run rather than isolate a benchmark or language effect.

The context scores expose a tradeoff that the resolution rate alone would hide. Final line recall is high at 77.90%, while line precision is 20.39%. The agent found much of the annotated code, but its selected context also extended well beyond those annotations. F1 remains 28.11%; useful surrounding code may be unannotated, but broad reading is still a reason to inspect precision alongside recall.

The search pair had already reached 77.07% line recall before repair. Adding confirmed repair reads raised it to 77.90%, while F1 moved from 28.16% to 28.11%. This comparison of stages shows that the search workers found most of the eventually covered annotated source. It does not tell us how many fixes a different search strategy would have produced.

Almost all model usage goes into repair

Recorded search-plus-repair model usage totals $338.88, or $0.6778 per task. The two search workers account for $5.68 across the run; repair accounts for $333.20, or 98.32% of recorded model usage. Failures and stopped attempts stay in both the cost and outcome totals.

In this configuration, making search cheaper on its own would affect a small part of the total. A more useful next question is whether better source selection can reduce the repair work while preserving resolution quality. That needs a controlled repair comparison; these results do not answer it yet.

The cost accounting uses recorded SDK model-usage values, including caching. It excludes compute, native-test containers and earlier strategy development, and is not a reconciled cash invoice.

How to read and verify this result

The submission is under review in the official ContextBench repository. Its format checks, aggregation from public inputs and replay of recorded inputs pass. Maintainers still need to review task coverage, source attribution and native-grading comparability before leaderboard publication. We are reporting the submitted measurements here without assigning CodeNib an official rank.

All 500 task annotations had been exposed during development. Three original development repairs are reused, with their selected-context exports assembled retrospectively; the other 497 retain their first repair executions. Reference fixes, native test patches and grading feedback stayed outside model inputs. Arbitrary shell-output source attribution remains partial, so the context scores describe the selected source supported by the submission's delivery evidence, rather than a complete inventory of everything the solver may have read.

The public package includes the exact task list, pinned evaluator and implementation versions, outcome records, usage receipts, and raw search and repair trajectories. Its aggregation and report checks run without model keys or Docker. Replaying those records verifies the submitted accounting; it does not rerun inference or the native tests. See the reproduction guide and review notes for the full protocol and limitations.
