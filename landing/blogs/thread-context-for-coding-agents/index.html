A GitHub Thread Costs an Agent by the Call, Not by the Token

How codenib threads prepares an issue or pull request for a coding agent without a model, and the four decisions the saving comes from.

A coding agent asked to take over a pull request starts by reading the thread: the description, the comments, the reviews, the checks, a log. With gh that is one tool call per piece, and every call sends the whole conversation so far back to the model. codenib threads, a preview in CodeNib 0.2.6, reads the thread once, by code, before the agent starts. On 76 pull request takeovers that cut input tokens by 21% with Codex and 45% with Claude Code. The agents found the files to change about as often either way.

Fetching ahead of the agent is the easy part. This post is about the harder part, deciding what goes into the document. On pull requests, fetching ahead without choosing costs more than it saves.

Two costs that pull apart

We gave agents the same thread in three ways: the agent reads it with gh, every event is pasted into the prompt unprocessed, or the prompt carries the prepared context.

On issues, pasting everything cost the same as the prepared context, within 2%, and both took about a quarter fewer input tokens than gh. Nothing in the pasted prompt was selected or shortened, so that saving is only the tool calls that no longer happen.

On pull requests, pasting everything was the most expensive of the three. With Claude Code the 76 tasks cost $17.49 pasted, $11.34 with gh and $8.37 with the prepared context. Check logs, bot comments and review comments, unprocessed, cost more than the calls they replace.

So preparing a thread means removing the calls and then choosing. The choosing is done by code, with no model: the same thread always gives the same document, and every line in it traces to the event it came from. Four decisions carry most of it.

1. Never cut the thread the agent is working on

The obvious way to meet a token budget is to shorten long posts. For the agent's own thread this backfires: an agent that sees an omission mark in the pull request it was asked to fix reads the pull request again with gh, and has then paid for both.

So the budget is not applied evenly. Posts in the thread itself stay whole until they pass three times the budget. The issues and pull requests it links to are cut first, oldest posts first. The second line of the document then tells the agent which case it is in. This is caddyserver/caddy#8024 on November 14, 2026, with […] where we left text out and the line wrapped to fit:

Coverage: this thread complete, linked threads partial.
Everything people wrote in #8024 is below in full; […]
Reading #8024 again with gh returns nothing more.

The last sentence is written to be acted on. A post omitted from a linked thread can be fetched by its id, and the thread itself needs no second read.

2. A failed log is mostly one line, repeated

A linter that finds one problem in 300 files prints 300 lines, and a build matrix fails the same way on six platforms. Keeping the last 200 lines of each failed log, as our pasted prompts did, fills the prompt with one message.

The context keeps only the lines around an error. It then compares them with numbers, paths and hashes blanked out: lines that begin alike are shown twice and counted after that. Jobs are compared the same way: when most of the failing lines of two jobs match, the failure is printed once with the names of the jobs that share it. Jobs are never merged by name, because a matrix runs several jobs under one name and merging could hide the one that failed.

This pull request changes two files in Caddy's file server. The lint error is in reverseproxy.go, and the Windows job stopped while downloading a module. Neither failure is about the change, and the agent can see that without opening a log.

3. Say where in the code, and on what evidence

People in a thread point at code in four ways: a stack frame, a review comment on a line, a file path, a name in backticks. The context finds these with regular expressions and resolves them against one commit of your clone, read through Git, so an edited working tree does not change the answer. A line is mapped to the innermost function or type that contains it.

These four are not equally reliable, and the list is ordered by that: stack frames first, then review positions, paths, bare names, and last the files a diff touches. A bare name is looked up first in the files the thread already mentions. A name defined in more than three places is ambiguous and is dropped. Each location names the event that pointed at it.

## Code locations
[…]
- modules/caddyhttp/fileserver/browse.go:85-229 `FileServer.serveBrowse()` (path; #8023/comment/6594174437)

Once locations are line ranges, a second question becomes cheap. codenib threads sync --open-pulls records which lines each open pull request changes. When one of those ranges falls inside a function the thread points at, someone else is changing that function now:

## Also in progress on this code
- #7777 (open PR by Jualhosting, updated 2026-10-26) fileserver: Improve 404 error detail and context — changes `FileServer.serveBrowse()`; also edits modules/caddyhttp/fileserver/staticfiles.go

An agent working one thread has no way to see this for itself, and it is common. In astral-sh/ruff, 30 of the 59 most recently updated open pull requests changed a symbol that another of them also changed.

In this preview the locations come only from what the thread says. They do not use CodeNib's code graph, so the context does not know what calls a function.

4. Keep events, not documents

Underneath, a thread is stored as an append-only log of events. Each event has a fixed address such as #8024/review_comment/4477879638, and an edited comment is appended as a new record under the same address. The document is computed from the log each time. Three things follow.

Every line can be checked. The bracketed ids in the excerpts above are addresses, and codenib threads events <id> prints the raw event.

Coming back is cheap. The document ends with a cursor, the address of the newest event it saw, and --since <cursor> returns only what came after it. Across 151 issues with a median of six returns each, a first context followed by updates took a median of 2,897 tokens over the life of the issue, against 21,103 for reading the thread again each time.

Many agents can share one store. A ticket is a piece of work that remembers its position in each log it follows. Two tickets on one thread store it once, and a comment edited after a ticket read it comes back as unread. A poll asks GitHub once which threads changed and fetches only those. With 24 tickets following 71 threads of astral-sh/ruff, fetching everything took 278 requests, and a poll with nothing new took 13.

Same answers, fewer tokens

Each task showed an agent a thread and the repository as they stood at a cut-off, and asked which files have to change. The answer was compared with what the merged pull request changed. Files found are listed for gh, pasted and the prepared context, in that order; token columns compare the prepared context with each of the other two.

The answers hold while the cost falls. With Codex the files found are the same. With Claude Code they are close, 0.80 against 0.83, a gap too small to tell from chance on 76 tasks. Pasting the whole thread shows the same small gap (0.78), so it comes from handing context over and not from what the context leaves out: an agent given the thread up front reads a little less code. The document therefore ends by telling the agent that it covers the threads and not the code.

The saving grows with the thread: on the 22 pull requests whose threads ran over 20,000 tokens, input tokens fell 34% with Codex and 63% with Claude Code.

Pull request tasks come from astral-sh/ruff, caddyserver/caddy and pydantic/pydantic; issue tasks from the first two. Claude Code ran Claude Opus 5.5 at medium effort. The result shows where an agent would work and what reaching that cost, not whether it then writes a better fix. Intervals, method and the script to reproduce it are in the thread context guide.

Try it

It needs CodeNib 0.2.6, Git, and either a GitHub token in GH_TOKEN or a signed-in gh. Run it inside a clone of the repository:

python -m pip install -U codenib

codenib threads context 812                        # write THREAD_CONTEXT.md before the agent starts
codenib threads show 812 --sync --since '<cursor>'  # later: only what changed
codenib threads open 812                           # or let a ticket remember what it read

Writing the file before the agent starts does not depend on the agent choosing to call a tool. For later reads, the CodeNib plugin for Claude Code and Grok Build adds /codenib:thread, and codenib threads mcp serves the same to any agent that speaks MCP.

CodeNib executes and follows nothing in a comment, but the text still reaches your agent, so give the agent no more permissions than you would when it reads GitHub directly. Every command and option is in the thread context guide.
