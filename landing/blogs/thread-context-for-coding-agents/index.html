Hand Your Coding Agent the Whole GitHub Thread in One Read

A preview in CodeNib 0.2.6: codenib threads prepares an issue or pull request for an agent once, with no model, and later returns only what changed.

Before a coding agent changes any code for an issue or a pull request, it has to learn what was asked, what the reviewers said, and why the checks fail. codenib threads prepares that once. On 76 pull requests taken over after a review or a failed check, handing the agent this prepared context cut its input tokens by 21% with Codex and 45% with Claude Code, against letting the agent read the thread itself with gh.

Why a thread costs more than its size

A GitHub thread here means an issue or a pull request together with everything attached to it: comments, reviews, review comments on lines of the diff, check results and their logs, and the other threads it links to. An agent reading one with gh fetches these a piece at a time, and it does not know which pieces exist until it has read the one before.

Each of those tool calls sends the whole conversation so far back to the model. The cost of reading a thread is therefore set by the number of calls more than by the size of the thread. A two-line comment that takes a fifth call to reach is paid for with everything the four calls before it returned.

codenib threads does the fetching ahead of the agent and writes one Markdown document inside a token budget. No model takes part: status comes from GitHub's events, code locations from the paths, stack frames, review positions and symbol names in the thread, and the failing lines from the check logs. Bot comments, quoted replies and passing checks are left out, and a paragraph that one thread repeats from another appears once.

A worked example on a Caddy pull request

caddyserver/caddy#8024 is an open pull request that fixes an open redirect in the file server. It closes one issue, a later pull request mentions it, and it has an approval, later review comments and two failing checks. Suppose an agent is asked to get it ready to merge. The excerpts below are the real output of one command, run in a clone of Caddy on November 14, 2026; […] marks lines we left out here.

Where it ends

This covers the threads, not the code. The locations above are only the ones the threads name; the change may reach further, so explore the code as you would without this context.
Cursor: #8285/referenced/35217640406. Bracketed ids cite thread events; fetch one with `codenib threads events <id>`, or later changes with `codenib threads show 8024 --since #8285/referenced/35217640406`.

The context closes by telling the agent what it does not cover, and with a cursor: the id of the newest event it saw. Every bracketed id in the document can be checked with codenib threads events.

Coming back, and many threads at once

Work on a thread rarely ends in one sitting. A reviewer answers, a check finishes, a new pull request appears for the issue. Passing the cursor back with --since returns only what happened after it. Across 151 issues with a median of six returns each, a first context followed by updates took a median of 2,897 tokens over the life of the issue, against 21,103 for reading the whole thread each time.

A ticket keeps that cursor for you. It starts from an issue or pull request, follows it and the threads linked to it, and remembers what it has read. We opened four tickets on Caddy pull requests:

What it measured

Each task showed an agent a thread as it stood at a cut-off and a snapshot of the repository at that moment, and asked which files and symbols have to change. The answer was compared with what the merged pull request changed. Three ways of supplying the thread were compared: the agent reads it with gh, every event is pasted into the prompt unprocessed, or the prompt carries the codenib threads context.

It saves tokens, more so on long threads. On short threads, pasting everything costs as little: issue takeovers with Codex came out level with pasting. For Claude Code the reported cost of the 76 pull request tasks was $8.37 with the prepared context, $11.34 reading with gh, and $17.49 with everything pasted.

It does not make answers better. With Codex the files found are the same. With Claude Code, the agent that read the threads itself found slightly more of them, 0.83 against 0.80. That gap is too small to tell from chance on 76 tasks, but pasting the whole thread shows it too (0.78), so it comes from handing context over: an agent given the thread up front runs fewer commands and reads less code. The context now ends with the line shown above, telling the agent that it covers the threads and not the code. If finding every file matters more to you than cost, let the agent read for itself.

Pull request tasks come from astral-sh/ruff, caddyserver/caddy and pydantic/pydantic; issue tasks from the first two. Both agents ran without network access, and no arm could see the pull request's own diff at the cut-off. Claude Code ran Claude Opus 5.5 at medium effort, once per arm. The result shows where an agent would work and what reaching that cost; it does not show that the agent then writes a better fix. Intervals, method and the script to reproduce it are in the thread context guide.

Try it

Thread context ships in CodeNib 0.2.6. It needs Git and either a GitHub token in GH_TOKEN or a signed-in gh. Run it inside a clone of the repository:

python -m pip install -U "codenib[mcp]"

codenib threads context 812     # write THREAD_CONTEXT.md before the agent starts
codenib threads show 812 --sync --since '<cursor>'   # later: only what changed
codenib threads open 812        # or let a ticket remember what it read

Writing the file before the agent starts does not depend on the agent choosing to call a tool, so use it for the first context. For what comes later there are three ways in:

  • Claude Code and Grok Build. The CodeNib plugin adds /codenib:thread, which the agent also uses by itself when you name an issue or pull request.
  • Any agent that speaks MCP. codenib threads mcp serves the context, tickets and raw events. It is a separate server from CodeNib's code search, so adding it leaves the agent's code tools as they were.
  • DeepSeek Harness and everything else. Write the file and tell the agent to read it first.

Thread text is treated as data: CodeNib executes and follows nothing in a comment, and only reads from GitHub. The text still reaches your agent, as it would if the agent read the thread itself, so anyone who can comment on a thread can address your agent. Give the agent no more permissions than you would when it reads GitHub directly.

The thread context guide has every command and option. To see what CodeNib does for the code itself, open a repository Wiki.
