# CodeNib 0.2.7

CodeNib 0.2.7 makes a local Wiki the place where you read a repository and
work with your coding agent. The Wiki opens with the repository's own README
and docs, and your Claude Code can write the other pages. Select words on a
page or lines of code to ask about them, request a change or leave a note;
your own Claude Code does the work, its answers and diffs come back next to
what you selected, and you review a change hunk by hunk. The change guard now covers Go, Rust,
JavaScript and TypeScript and can write its report as a pull-request comment,
Wiki pages show the issues and pull requests on the code they explain, and an
MCP server keeps answering from its graph after you edit the source.

Upgrade the environment running CodeNib and restart its MCP client:

```bash
python -m pip install --upgrade "codenib[graph,mcp]==0.2.7"
codenib --version
```

## Your docs first, and pages your Claude Code writes

A local Wiki starts with the repository's README and the Markdown files under
`docs/`, as pages under **Repository docs**, in the order `mkdocs.yml` lists
them when there is one. Without a model, the other pages are built from the
code index. Add `--generate` to have them written: with Claude Code installed
and signed in, they are written on your Claude Code plan with no API key, the
Overview first and the rest in the background, at roughly $0.10 to $0.20 a
page.

```bash
codenib wiki . --generate
```

The Wiki follows your working tree. When files change, from an applied change
or an edit in your editor, it updates its index within a few seconds, and a
page whose code changed is written again the next time it is opened.

## Ask your agent from the Wiki

Start a local Wiki with `codenib wiki .`, or `/codenib:wiki` in Claude Code,
and open the address it prints. Select words on any page, or lines of code in
the source panel, and pick **Ask**, **Change** or **Note**.

- A question goes to your Claude Code, which reads the code and answers under
  your question. The code it cites opens in the source panel, and you can
  reply to ask a follow-up.
- A change request runs in a separate git worktree, so your working tree
  stays as it was. Review its diff hunk by hunk: apply or discard each one, or
  the rest at once. Other pages that cite the changed lines get a note that
  links back to the request.
- A note is a standing fact, such as "this path must stay lock-free". Every
  later task on the same page includes it, and the agent is told not to
  contradict it.

**Add to page** puts an answer into the page under its question, and **Edit
page** opens the page's Markdown. Your edit is kept when the Wiki is written
again, and the page tells you when the generated text has changed since.
Annotations follow what they sit on: when code moves they move with it, and
when it is edited or deleted they say so.

The agent gets file tools only, with no shell or network tools, and runs on
your own Claude Code sign-in; CodeNib asks for no API key. Annotations and
tasks are plain files under `.codenib/` in the repository, so you can commit
them to share them or ignore them to keep them local. The address carries a
session key that annotating needs, so no other page in your browser can start
your agent. See [Ask your agent from the Wiki](https://docs.codenib.ai/quickstart/#ask-your-agent-from-the-wiki).

## The change guard covers more languages and reviews

`codenib guard` now reaches Go, Rust, JavaScript and TypeScript code as well
as Python. It also reaches an override from a call made through its base
class, the special methods an operator runs, and methods a call on a value of
unknown type may run. On 68 agent regressions it lists a broken test for 42,
up from 38.

`codenib guard check --markdown` prints the report as a pull-request comment:
the callers a change left alone and the tests that exercise the edited code,
read from the base commit's code graph without a model.

## Threads on the Wiki

A Wiki page now ends with the open issues that point at the code it cites, the
open pull requests that change that code and the merged changes that last
touched it, and the Wiki map marks where that activity is. Build the join with
`codenib threads overlay`; it uses git and the stored thread logs and needs
neither a model nor a code graph. Agents that work thread tickets unattended
can claim them under a lease with `codenib threads inbox N --claim` and
acknowledge them with `codenib threads ack`, and thread context names each
author's role in the repository.

## Graphs that keep up with edits

An MCP server started with `--defer-graph` keeps answering from the graph it
has after a source edit and names the files that changed since it was built,
instead of waiting minutes for a rebuild. With
`CODENIB_GRAPH_INCREMENTAL=builder`, a stale Python graph is patched by
rebuilding only the changed files with its own builder; on thirteen real
commits the result equals a fresh build. A full build now reports when the
graph is cut off from its source.

## Also in this release

- On a Mac, `pip` installs CodeNib from its source distribution. Each release
  is now checked on macOS: that install runs the Wiki, saves a note and builds
  the Dependency Map.
- Install the Wiki as an app from your browser: it opens in its own window
  with the CodeNib icon, and shows an offline page when its service is not
  running.
- An Overview page with generated figures builds them once for each index and
  then opens at once, instead of rebuilding them on every visit.
- Codex installs the CodeNib plugin with `codex plugin marketplace add` and
  `codex plugin add codenib@codenib`.
- The Wiki shows code walkthroughs where they have been built, and its
  Overview path starts where the README points.
- Optional contextual BM25 indexing, a SeeRepo graph adapter, and native runs
  with official scoring for SWE-QA, SWE-QA-Pro and CORE-Bench.
- Windows fixes for git output, hook commands, file locks and renames.
- Unused agent skills and the agent-compile sweep tooling are removed; Ask and
  the evaluation harnesses keep the nine skills they use.
