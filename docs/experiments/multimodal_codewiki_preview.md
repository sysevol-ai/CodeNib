# Multimodal CodeWiki preview

This note shows how to preview CodeNib's source-grounded editorial Wiki layer.

The media contract is provider-neutral, but the first choice is now the
repository's own visual language. On an Overview page, CodeNib looks for a
meaningful image already referenced by the repository README, validates it,
and places it between the opening thesis and the detailed story. Planned
`media_slots` can still be materialized by the local deterministic SVG renderer
or by an OpenAI-compatible image endpoint when the repository has no suitable
asset or the page needs a more focused explanation.

![Multimodal CodeWiki preview](multimodal-codewiki-preview.svg)

## What reviewers should see

Open `Overview` for a repository whose README includes an architecture,
workflow, overview, or product image. The page should read in this order:

1. title and opening thesis;
2. one repository-provided lead visual, when a suitable asset exists;
3. one semantic system-architecture view synthesized for Overview only;
4. the source-backed implementation story;
5. provenance, subsystem navigation, and source evidence.

The lead image must be shown without cropping and labeled `Provided by
repository`. Its README reference and asset path remain visible as provenance.
The generated architecture view is not a call graph and is never inserted into
a child page. It names the system's architectural roles, separates their
layers, follows one semantic runtime path, and calls out only supported
external dependencies and boundaries. Static call relations remain source
evidence beneath that synthesis; they are not promoted into architecture
cards. When the evidence cannot support the synthesis, CodeNib omits the view
instead of falling back to a generic storyboard or a decorated call graph.
With `CODENIB_WIKI_MEDIA_MODEL=local/svg`, the same typed contract also receives
a downloadable deterministic SVG.

Each slot keeps enough metadata for review and later model replacement:

- `kind`, `placement`, `title`, and `purpose`;
- source citations used to ground the visual asset;
- an optional versioned `render_contract` whose adapter-specific data is the
  complete input to a deterministic diagram, storyboard, or chart;
- editable `human_prior` notes for later human refinement;
- generated asset provenance, including provider, model, prompt, URI, and
  source citations. The local cache manifest separately binds the render
  inputs, prompt, and generated bytes with SHA-256 digests.

Repository assets use the same slot shape with `provider: "repository"` and
`model: "repository"`. They do not carry a generation prompt.

## Editorial compilation workflow

The Wiki should evolve as a compiler with reviewable intermediate forms, not
as one prompt that writes an entire Markdown page:

```text
authenticated repository snapshot
  -> evidence pack (symbols, relations, README claims, repository visuals)
  -> story plan (thesis, reader questions, beats, evidence allocations)
  -> Overview architecture synthesis (roles, layers, path, boundaries)
  -> visual plan (typed data contract, placement, renderer)
  -> renderers (repository asset, native HTML, deterministic SVG)
  -> grounding and visual-quality gates
  -> reader layout (lead, section, aside, appendix)
  -> live API and static export
```

The rollout is deliberately incremental:

- **Slice 1 — repository visual lead (implemented):** discover README images,
  rank architecture/workflow/overview assets above decoration, reject external
  and unsafe paths, validate bounded raster payloads, and preserve live/static
  parity.
- **Slice 2 — editorial story IR (implemented in preview):** replace a flat
  section list with an explicit thesis, audience question, narrative beats,
  transitions, and a compiler-derived evidence budget. Planned Overview
  stories are publication-gated; legacy and deterministic pages receive the
  same versioned contract in shadow mode without invented transition prose.
- **Slice 3 — renderer adapters (implemented in preview):** the Overview
  architecture adapter receives typed, bounded roles, semantic connections, a
  primary path, and explicit boundaries. Every element carries evidence. The
  local SVG renderer renders only typed contracts; it never turns an untyped
  concept prompt into a generic placeholder diagram.
- **Slice 4 — page-level quality gates (shadow gate implemented):** prose
  quality still gates generated text. The serialized `visual_quality` report
  now separately checks contract validity and whether Overview has a
  materialized repository-owned or typed visual. A missing visual is visible
  to audits and reviewers but does not hide otherwise valid prose during the
  rollout. The architecture contract renders natively as a readable primary
  path with supporting roles and boundaries; the downloadable SVG uses the
  same data. Child pages have no automatically generated architecture or
  storyboard slot.

This separation is what lets the team judge each improvement independently. A
poor image choice can be fixed in selection without rewriting prose; a weak
story can be replanned without changing retrieval; and a renderer can be
replaced without changing the page contract.

## Editorial story contract

The planner no longer hands the renderer an unordered bag of sections. It
returns one `story` object alongside the grounded fact plan:

```json
{
  "version": 1,
  "origin": "planned",
  "reader_question": {
    "statement": "How does `Entry.start()` move input through the runtime?",
    "evidence": ["E1", "E2"]
  },
  "beats": [
    {
      "section": "Public entry",
      "role": "entry",
      "evidence": ["E1"]
    },
    {
      "section": "Runtime handoff",
      "role": "handoff",
      "transition": {
        "statement": "The prepared input then crosses into the runtime",
        "evidence": ["E1", "E2"]
      },
      "evidence": ["E1", "E2"]
    }
  ],
  "evidence_budget": {
    "available_source_evidence": 8,
    "allocated_source_evidence": 6,
    "beat_coverage": 1.0,
    "max_beat_reuse": 0.5
  }
}
```

The model authors the question, beat order, roles, and transitions. CodeNib
then admits them against the same evidence as ordinary claims, drops
unsupported connective prose, aligns beats to sections that survived source
checks, and computes the budget itself. The Markdown adapter places the reader
question after the thesis and a transition at the start of each later beat.

The quality report exposes question validity, section/beat alignment, role
progression, transition coverage, per-beat evidence coverage, and evidence
reuse. If a new Overview supplies a planned story, those checks are blocking.
The question must also appear in the rendered Markdown; a valid hidden JSON
field no longer satisfies the page gate. A three-beat story needs at least one
explicit grounded bridge, while longer stories need bridges across at least
half of their gaps. Section order and headings carry the remaining continuity
without forcing repetitive transition prose.
Pages from older caches or the deterministic builder use `origin: "inferred"`
or `"derived"`; they preserve API/static-export parity but remain a visible
shadow result until their prose is replanned. This staged gate is intentional:
it lets reviewers compare the reading experience before making story planning
mandatory for every page.

## Overview editorial budget

Retrieval remains broad so planning can compare the repository's real entry,
mechanism, and outcome. Publication is deliberately narrow. The Overview
compiler applies these deterministic limits after source admission:

- 2–4 complementary content sections;
- at most 4 claims total and at most 2 in any section;
- no section lead, source excerpt, or code fence;
- one thesis, one rendered reader question, at least two source evidence items
  when the evidence pack contains them, and one validated semantic
  architecture plan; and
- at most two related-page links.

Two sections are valid when the thesis already supplies the opening stage; the
compiler does not manufacture a third section to satisfy a quota. Model plans
may inspect more symbols and relations, but unused evidence stays out of the
body. Repetitive transition/claim pairs are rendered once.

## Typed renderer contracts

The planner selects a renderer only after it has admitted the underlying
facts. Every deterministic visual carries schema version `1`, an adapter, a
provenance class, a page-local evidence list, and adapter-specific data. The
Overview architecture synthesis is represented as:

```json
{
  "schema_version": 1,
  "adapter": "architecture",
  "provenance": "architecture-plan",
  "evidence": ["E1", "E2", "E3", "E4", "R1", "R2", "R3"],
  "data": {
    "nodes": [
      {"id": "question_interface", "label": "Wiki and Ask interface", "detail": "Accepts repository questions", "layer": "interface", "kind": "frontend", "evidence": ["E1"]},
      {"id": "evidence_planner", "label": "Evidence planner", "detail": "Plans grounded repository work", "layer": "coordination", "kind": "backend", "evidence": ["E2"]},
      {"id": "source_indexes", "label": "Hybrid source indexes", "detail": "Retrieves graph and lexical evidence", "layer": "data", "kind": "database", "evidence": ["E3"]},
      {"id": "answer_renderer", "label": "Grounded answer renderer", "detail": "Returns source-linked findings", "layer": "execution", "kind": "backend", "evidence": ["E4"]}
    ],
    "edges": [
      {"source": "question_interface", "target": "evidence_planner", "label": "frames the question", "evidence": ["R1"]},
      {"source": "evidence_planner", "target": "source_indexes", "label": "requests relevant evidence", "evidence": ["R2"]},
      {"source": "source_indexes", "target": "answer_renderer", "label": "supplies cited findings", "evidence": ["R3"]}
    ],
    "primary_path": ["question_interface", "evidence_planner", "source_indexes", "answer_renderer"],
    "boundaries": [
      {"id": "index_boundary", "label": "Index boundary", "detail": "Planning remains separate from persisted retrieval views", "members": ["evidence_planner", "source_indexes"], "evidence": ["E2", "E3"]}
    ]
  }
}
```

The current adapters enforce different invariants:

- `architecture-plan`: 4–10 semantic roles across at least three declared
  layers, a connected 3–7 role primary path, evidence-backed responsibilities
  and connections, and at most three evidence-backed boundaries; labels that
  look like files or callables, copied prompt-placeholder roles, and generic
  `calls`/`imports`/`depends on` connections are rejected;
- legacy relation architecture: still accepted at the low-level contract
  boundary for compatibility, but never selected by the Wiki media planner;
- `flow`: 2–7 nodes connected as exactly one directed, acyclic path;
- `storyboard`: 2–8 ordered panels, each backed by the evidence allocated to
  its final story beat; and
- `bar-chart`: 2–10 unique labels with finite, non-negative, evidence-backed
  numeric values.

The Wiki planner selects only `architecture-plan`, and only for `overview`.
Static relations may support a semantic connection, but component roles and
boundaries must also be grounded in source evidence. A child-page flow,
storyboard, Mermaid block, or relation map never becomes an automatic media
slot. No arbitrary Mermaid or raw SVG supplied by a model is executed. Concept
illustrations remain valid inputs for an external image provider, but
`local/svg` deliberately leaves an untyped concept slot unmaterialized instead
of presenting a stock image as a repository-specific explanation.

A selected repository-owned lead still suppresses materialization of an
additional generated *lead*. The semantic architecture uses `aside` placement,
so it can follow a repository image without competing with it: the first keeps
the project's own visual language, while the second explains CodeNib's
source-backed understanding of roles, path, and boundaries.

The live endpoint writes the resulting SVG and a digest-bound manifest to its
media cache. Static export calls the same adapter in memory, adds the SVG bytes
to the atomic export inventory, and emits the same slot and asset shape. An
invalid contract is removed before a provider call; only a bounded rejection
report remains in `visual_quality`. Derived media plans carry their own version,
so an older cached page can adopt new placement or renderer rules without
regenerating its prose or calling the language model again.

The local renderer uses the `editorial-svg-v5` design system: warm paper,
hairline structure, charcoal serif titles, restrained layer accents, and an
integrated source note. The native view and SVG both give the primary runtime
path most of the space, then separate supporting roles and explicit boundaries
into a quieter column. Responsibilities remain readable prose; callables and
file paths never become the visual hierarchy. The layout is vertical on narrow
screens, preserving type size instead of compressing the architecture into a
dense 16:9 storyboard.

## License boundary

CodeNib's project license is Apache-2.0; that is a permissive open-source
license that permits commercial use, not a label saying the project is a
commercial distribution. This workflow follows the information boundary made
explicit by [Archify](https://github.com/tt-a1i/archify): architecture models
components, services, storage, dependencies, and boundaries, while a call
chain belongs to a separate sequence view. CodeNib implements that distinction
with its own Apache-2.0 data contract, native layout, and SVG renderer. It does
not copy Archify's MIT-licensed templates or assets. Copying source, SVG
templates, fonts, screenshots, or other assets is a different decision: each
item must have an identified license, the relevant notices and attribution
must be preserved, and reciprocal-license obligations must be evaluated for
the intended distribution. The current adapters copy none of the referenced
projects' code or visual assets, so renderer evaluation and dependency/license
evaluation remain separate review steps.

## Repository visual safety boundary

CodeNib never downloads a README image during page generation. Relative paths
are resolved inside the checkout; a `raw.githubusercontent.com` or GitHub blob
URL is accepted only when it names the same repository and maps back to a local
file. Static export additionally requires that file to be in the authenticated
source inventory. Badges, logos, sponsor art, traversal, SVG, mismatched file
signatures, and oversized files are rejected. Live pages serve only the
selected asset through a bounded route. Static export copies the same
authenticated bytes and rewrites the slot URI into the export tree.

## Minimal local preview

From a CodeNib checkout:

```bash
export CODENIB_WIKI_MEDIA_MODEL=local/svg
codenib wiki /path/to/repository
```

The `codenib wiki` command starts the backend and frontend. After the page
opens, select a Wiki page and check the `Multimodal CodeWiki` section.

The local SVG path writes generated assets under:

```text
<data_dir>/wiki_media/
```

The backend serves those files from:

```text
/api/repos/{repo_id}/wiki-media/{page_id}/{filename}
```

## API smoke check

After the local Wiki is running, identify a repo id:

```bash
curl -s http://127.0.0.1:8000/api/repos | python -m json.tool
```

Then inspect a Wiki page payload:

```bash
curl -s http://127.0.0.1:8000/api/repos/<repo_id>/wiki/overview \
  | python -m json.tool
```

The response should include `media_slots` and `visual_quality`. A
repository-provided Overview lead looks like:

```json
{
  "id": "overview-repository-visual",
  "placement": "lead",
  "asset": {
    "provider": "repository",
    "model": "repository",
    "mime_type": "image/png",
    "uri": "api/repos/<repo_id>/wiki-source-assets/docs/architecture.png",
    "metadata": {
      "origin": "repository",
      "source_path": "docs/architecture.png"
    }
  }
}
```

The same response now also includes `story`. For a freshly planned Overview,
look for `origin: "planned"`, one beat per rendered content section, and
`quality.story_valid: true`. Static and deterministic pages still include the
field, with `origin: "derived"`, so clients never need separate contracts.

With the local SVG provider enabled, supported generated slots also include an
`asset` object similar to:

```json
{
  "provider": "local",
  "model": "local/svg",
  "mime_type": "image/svg+xml",
  "uri": "api/repos/<repo_id>/wiki-media/overview/<slot>.svg",
  "source_citations": ["..."],
  "metadata": {
    "deterministic": true,
    "adapter": "architecture",
    "visual_schema_version": 1
  }
}
```

The slot immediately above that asset contains its `render_contract`.
`visual_quality.publication_ready` is true for Overview only after either a
repository-owned lead or a valid typed visual has actually been materialized.
Static exports materialize typed SVGs automatically, so the same contract is
visible without a media service.

## Optional OpenAI-compatible image endpoint

The same slot contract can be materialized by a provider that implements an
OpenAI-compatible `/images/generations` endpoint:

```bash
export CODENIB_WIKI_MEDIA_MODEL=<image-model-name>
export CODENIB_WIKI_MEDIA_API_BASE=http://127.0.0.1:8080/v1
export CODENIB_WIKI_MEDIA_API_KEY=<optional-api-key>
codenib wiki /path/to/repository
```

The UI and API payload stay the same; only the asset provider/provenance changes.
The first uncached page request calls the configured provider; later requests
reuse the validated local manifest. Provider responses, decoded images, prompt
size, slot count, timeout, and image dimensions are bounded. Hosted asset URLs
must use HTTP(S), and generated local files are written atomically and served
with restrictive content headers.

## Gemini native image generation

CodeNib can also materialize the same source-grounded slots through Gemini's
native Interactions image API. This is a separate generation backend; it does
not replace the visual embedding model used by the multimodal vector view.

```bash
export CODENIB_WIKI_MEDIA_MODEL=gemini-3.1-flash-image
export CODENIB_WIKI_MEDIA_API_KEY=<gemini-api-key>
export CODENIB_WIKI_MEDIA_OPTIONS='{
  "provider": "gemini",
  "aspect_ratio": "16:9",
  "image_size": "1K",
  "mime_type": "image/jpeg"
}'
codenib wiki /path/to/repository
```

The official Gemini endpoint is selected when `CODENIB_WIKI_MEDIA_API_BASE` is
unset. The adapter sends the slot prompt and server-side source evidence as one
typed text input, requests one inline image, and sets `store: false`. It accepts
only bounded JPEG output matching the configured MIME type. The local
asset manifest records the model, provider, generation options, prompt/render
digests, content digest, source citations, and the fact that provider-side
interaction storage was disabled.
