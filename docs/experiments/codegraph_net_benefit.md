## Current iteration objective

On 2026-10-29 the maintainer authorized continued product iteration toward a
repeatable advantage over Serena and the native agent. Keep the original
cohorts and all negative outcomes frozen. The objective is verified whole-task
benefit, rather than a positive result on an exposed task or a faster isolated
graph operation. The external five-user gate remains separate and enrollment
is still zero; engineering work does not authorize outreach.

The [model-free attribution](codegraph_cost_attribution_v2_2026_10_29.json)
verifies all twelve captured v2 receipts. Of CodeNib's 99.006-second observed
gap to Serena, 73.419 seconds (74.2%) is extra setup. CodeNib's setup contains
58.861 seconds in initialization/indexing/registration and 23.335 seconds in
language-provider preparation; these command durations are not interchangeable
with pure compiler time. The task phases add 29.927 seconds while the remaining
session/orchestration component is 4.340 seconds lower. Neither product is
called. Tool-schema exposure and task latency causation remain unknown.

Even removing all CodeNib setup, while holding recorded task execution fixed,
leaves 581.688 seconds versus Serena's 567.999 seconds. This optimistic
arithmetic scenario is not a new run or score. Startup work alone cannot meet
the required benefit on this cohort.

Work proceeds through these gates:

   and source receipts, source-currentness checks, original grades and costs.
2. Reduce unused startup work. Any deferred index must include its actual
   first-call and later-update costs in the measured workflow. A missing
   provider or partial graph must remain explicit.
3. Test tool discovery and useful query composition. The first candidate wires
   the existing explore-only tool list into managed agent initialization,
   preserving the default full list and registration ownership. Its indexed
   single-entry mode now requests upfront loading through the documented
   Claude tool metadata, with an explicit client override. The user-funded
   grep/Jev route keeps its existing discovery policy. Model-free
   registration/protocol checks establish functionality only. Record optional
   tool use and reading/model turns before attributing an effect to this mode.
4. Use exposed sources only for development diagnostics. Freeze independent
   confirmation task membership, acceptance criteria, tool visibility, exact
   model/runtime identities, deadlines, costs and the primary endpoint before
   inference. Keep native tools available, and apply any exposure policy fairly
   to competitor tools. Do not force product calls or revise grading to obtain
   a positive result.
5. Require acceptance at least as good as the strongest eligible alternative,
   no additional serious error, at least 20% lower complete task wall time and
   no greater than 10% normalized-model-usage regression. Preserve setup,
   timeout, failure, update and retry costs. Confirm the advantage on a second
   independent frozen set before declaring this engineering objective met.

Use the authorized subscription SDK where available. Retain the original $500
paid-API ceiling, distinguish SDK estimates from invoices and disallow an
unrecorded API-key fallback. Each model round needs a bounded resource ledger
and current official provider constraints. Freeze each round before inference; passing unit checks alone does not
establish efficacy. A failed or inconclusive iteration stays recorded and

Current state: original-cost attribution is complete; the opt-in discovery

## Product question and decision

Can a developer complete source-grounded coding tasks more effectively with
CodeGraph after paying its setup, indexing and update costs? The supported
initial scope is source-current definition/reference navigation and selecting
related code for call-path or change-impact inspection. A static reference
alone does not establish invocation or a complete runtime path. Public entry,
comparison and MCP guidance reflect that scope, keep native exact search
available, and distinguish a first connection check from ordinary tool choice.
This pilot produces a promote, narrow, no-go or insufficient-evidence decision.
It does not promise a positive result or establish population-wide efficacy.

The pilot product gate is at least 20% improvement on prospectively selected
complete task wall time against the
strongest eligible alternative. Task acceptance must not fall; any additional
serious correctness error blocks promotion. Fixing a recorded issue or
publishing this plan does not satisfy that gate.

## G3: five-user repeat-use pilot

Maintainers own recruitment and consent. The user confirms there is currently
no recruitment program. No invitation has been sent and no
participant is claimed. Each of five participants attempts setup on their own
repository and has a seven-day observation window after first use.

Recruitment hand-off is prepared below; it has not been sent. Maintainers must
confirm volunteers and consent before starting any observation window:

> We are inviting five developers to try CodeNib on their own repository for
> seven days. Use it only when it helps your normal work; no repeated-use quota
> is required. Participation is voluntary and you can stop at any time. With
> your consent, we will record setup time, whether your agent used the tool,
> whether its answer helped, errors/help needed and later voluntary reuse.
> Private source, credentials, prompts and identifiable repository paths are
> excluded by default. Agree any additional shared evidence separately.

For each consenting volunteer, keep an anonymous participant ID, consent/date,
language and approximate repository size, first-use date and observation end.
Retain unsuccessful setups and withdrawals with their stated reasons. Use the
same short check-in fields for each observed work session: task category,
actual tool call, accepted source-linked answer, help needed and later reuse
without a reminder to invoke CodeNib. Do not infer use from installation alone.

Record setup attempts/successes, time to the first accepted source-linked query,
whether the agent actually called the tool, maintenance help needed and
voluntary return on later work. Target at least three of five returning without
a reminder to invoke CodeNib for the measured task. Keep all enrolled users in
the denominator and label missing observations. This is an adoption pilot, not
an estimate of market retention.

Use consented receipts/interviews; do not add a telemetry platform or collect
private source by default. Website views, setup-link clicks, operator demos and
stars do not count as successful own-repository use.

## G4: review and product action

- **Promote:** G1 correctness, the frozen G2 net-benefit gate and G3 repeat-use
  acceptance pass. Publish the supported scope, costs and reproducible evidence.
- **Narrow:** a prospectively declared task group benefits, while broader work
  does not. Limit the product promise and default entry to the supported scope.
- **No-go:** an admitted pilot fails the gates. Record the result and reduce
  investment in the unsupported default rather than adding features to evade it.
- **Insufficient evidence:** configuration, costs, correctness or user observations
  are incomplete. Keep the objective active with explicit gates; missing data is
  neither a performance failure nor proof of benefit.

The review must reconcile code, local verification, documentation, PRs/issues
and any release decision. External recruitment or paid execution is a real gate;
planning artifacts and one merged fix cannot complete this objective.
A recorded correctness or performance failure can justify no-go before external
recruitment. Record unrun phases explicitly without claiming repeat-use evidence.
Insufficient evidence alone does not complete the objective.
