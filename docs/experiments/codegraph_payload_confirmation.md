## Work and acceptance

Each repository has five ordered tasks: implementation lookup, a selected
cross-file flow, change impact with two existing test examples, repair of the
public issue, and review after the same controlled helper addition. This is
fifteen tasks per arm, twelve complete workflows and sixty task attempts.
Lookup uses a fresh client; the other four tasks share a return client.
The repair patch is captured before the helper addition. All model workflows
terminate before private native grading or source-answer review begins.

Native read, search, shell and edit tools remain available in every condition.
Optional product calls are voluntary. Source fixtures expose only their exact
original commit. Each target has its own checkout and no SDK home, credentials,
grading directory, other arm or Docker socket. Bridge networking permits
declared provider/project-dependency installation; this is a source-access
policy, not OS network isolation.

Every read-only answer must satisfy the prompt criteria, preserve source and
support all material source claims with accurate current repository-relative
1-based ranges. Final answers must contain fewer than 350 words for lookup,
700 for flow/impact, and 400 for post-edit review, counted with Python
`str.split()`. Successful SDK completion alone is not acceptance. The source
rubric binds 31 original implementation/test anchors outside model mounts;
existing test examples are not an exclusive answer list. A prospective
clarification retains its original draft: absence of a zero-threshold guard
in Pylint's pair iterator does not prove duplicate findings at zero. No task
prompt, native test, selected denominator or endpoint changes. One unblinded
maintainer-agent reviews source claims; no independent adjudication is claimed.

The primary endpoint is complete five-task workflow wall time, from before
product installation through final SDK disconnect. Include actual connection,
index/provider preparation, edits, explicit updates, failures and retries.
Common prepared project dependencies and private grading are recorded
separately. Keep raw time and the existing remaining-deadline penalty for
failed/unattempted tasks; omitted work cannot become a zero-cost winner.

Promotion still requires correctness parity, no additional serious source
error, at least 20% less complete time against the strongest complete eligible
alternative, and at most 10% normalized model-token regression. Eligibility
still requires accepted tasks/native repairs and no material source error
across the full workload. No eligible alternative means insufficient evidence.
Do not select a favorable subset or loosen this rule after outcomes. Tasks
within a repository are correlated. This prospective set can supply at most
one independent success confirmation; a further disjoint success remains
required.
