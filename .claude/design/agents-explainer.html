An agent is a loop wrapped in a workflow.

The concepts behind long-horizon agents — the loop, the harness, context engineering, sub-agents, and orchestration — and how they assemble into the design at the heart of the Repository Guardian: a workflow that drives a sequence of memory-carrying loops.

loop = autonomous · model-driven workflow = deterministic · code-driven memory = persistence across time

Grounded in Anthropic's Building Effective Agents & Effective Context Engineering, Claude Code Skills docs, and LangGraph. Framing/analogies flagged where noted.

Part I · What an agent is

The agent loop

The core cycle: the model reasons → picks an action/tool → executes → observes the result → reasons again, until a stopping condition. Anthropic's own definition of an agent is precisely this — "LLMs autonomously using tools in a loop." It's non-deterministic: the model chooses the next action at each step, so the same task can take a different path each run.

single LLM call

static input → one response. No feedback, no self-correction — it just guesses.

agent loop

gets “ground truth” from the environment each step (a failing test, a missing file) and adapts. That feedback loop is the whole difference.

example · fix the failing testrun test → see NameError → add the import → rerun → green → stop. A single call would just guess a patch with no chance to run anything.

Why it matters for a persistent agent: the loop is the unit of autonomy — a long-horizon agent is this loop run hundreds of times, so stopping conditions and per-step feedback quality decide whether it converges or spins.

ReAct (Yao et al., 2022) is the specific reason-then-act technique that popularized this; the modern “agent loop” generalizes it.

The harness

Everything around the model that makes the loop happen — the runtime scaffolding. If the model is the brain, the harness is the body and nervous system. Same model in a better harness = a dramatically better agent, which is why harness engineering is its own discipline (Claude Code and SWE-agent's ACI are harnesses).

examplethe model emits run_bash("pytest") — the harness parses it, runs the subprocess, truncates the output, appends it as an observation, checks the turn budget, and only then calls the model again.

Why it matters: long-horizon reliability lives in the harness — retries, budget enforcement, state persistence, context compaction. Getting the harness right matters more than the model swap.

Tools vs. skills

A tool is a single function the model can call, exposed as a typed schema (read_file(path)). A skill is a packaged capability — a bundled workflow + instructions (Claude Code's SKILL.md) that the agent pulls in on demand. The key difference: a skill's body loads only when used, so you can hand the agent a long procedure without paying its tokens up front.

tool

one typed function call

edit_file(...) — one atomic action the model emits mid-loop and the harness runs.

skill · “CLI skill”

a workflow bundle, invoked

/code-review — its SKILL.md loads a whole procedure, which then fans out into many underlying tool calls. Model-invoked (auto-selected) or user-invoked (slash command).

Note (Claude Code, 2025→26): custom slash-commands and skills merged — /deploy can come from a command file or a skill; skills are the superset (add supporting files + invocation control + sub-agent execution).

Why it matters: skills encode hard-won, repeatable procedures as versioned, on-demand context — keeping the standing context lean while complex workflows are one invocation away.

Part II · What an agent sees

Context engineering — “not just prompt engineering”

Assembling exactly the right information into the finite context window on every inference, and compacting it as the loop runs. Anthropic (Sep 2025) frames it as replacing prompt engineering for agents: the question shifts from “what words?” to “what configuration of context is most likely to produce the desired behavior?” Prompt engineering is one-shot; context engineering is continuous, because a looping agent keeps generating data that must be cyclically refined down to “the smallest set of high-signal tokens.”

exampledon't dump a 50-file repo in the prompt. Keep only the system prompt, tool schemas, the task, and the ~5 files in play — and compact history when it nears the window limit, instead of letting stale tool output crowd out signal.

Why it matters: on a long horizon the window will fill. Success is bounded less by prompt cleverness than by what you keep, retrieve, summarize, or drop at each step. (This is the same problem the Guardian's memory layer solves — paged/summarized reads.)

Starting context

What the agent begins each run with, before any action: the system prompt (role, rules), the tool definitions (its action space), and any seeded state/memory (project docs, retrieved refs, prior-session memory). It's the “genome” every loop iteration inherits.

examplean agent whose starting context has a run_tests tool + the rule “always run tests before declaring done” verifies its work. Give the same model only edit tools and no such rule, and it confidently ships broken patches. Same model, different starting context, different agent.

Why it matters: it's inherited by every iteration and every compaction — a missing tool cannot be called, a missing rule won't be followed. A wrong starting context silently corrupts thousands of downstream steps.

Part III · How work splits

Sub-agents

A separate agent instance the parent spins up for a scoped task — with its own system prompt, own context window, own tool allowlist — that does the work independently and returns only a result, not its transcript. (In Claude Code: a markdown file under .claude/agents/ whose body is the sub-agent's system prompt.) Four reasons to delegate: isolate context, specialize, parallelize, and protect the parent's finite window.

exampleyour agent needs the callers of deploy(). It delegates to an Explore sub-agent, which burns 30k tokens grepping and returns a 15-line list. The parent's context grows by ~15 lines, not 30k tokens.

Why it matters: context isolation is the main lever that lets a long-lived agent do huge amounts of work without exhausting or polluting its own working memory.

the point engineers miss · starting context of a sub-agent

A sub-agent does NOT inherit the parent's history. It starts fresh; the parent constructs exactly what it needs — an objective, the relevant snippets, an output format, allowed tools — and gets back only the summary. Isolation is a feature: clean focus, no pollution, bounded cost.

Sub-agent vs. recursive agent

Both “call out to do more work,” but they're structurally opposite. The clean mental model: recursion = the same function calling itself on a subproblem; a sub-agent = a different function you hand a bounded task to.

⚠️ “Recursive agent” is a conceptual/architecture pattern, not a named product feature. “Sub-agent” is a documented feature (Claude Code, LangGraph subgraphs, OpenAI agents-as-tools).

Agent teams

Multiple specialized agents collaborating toward one goal — planner, coder, reviewer, researcher — under an orchestration pattern: supervisor / orchestrator-worker (a lead delegates), network / handoffs (peers pass control), or hierarchical (supervisors of supervisors). They talk via messages, handoffs, or shared state.

The trade-off (and why it matters): teams buy specialization + parallelism for decomposable work — but budget for a ~15× token bill and coordination logic. Multi-agent only pays off when task value absorbs that multiplier; it's wasteful for cheap or tightly-coupled tasks.

LangGraph multi-agent — the longer version

The confusing phrase is “stateful graph.” Here's the whole idea in one breath: instead of letting the model free-run in a loop, you draw the control flow yourself as a graph — boxes (steps) and arrows (what runs next) — and one shared record is passed from box to box, each box reading it and writing its change back. A free-form loop is “model, decide everything.” LangGraph is “I've drawn the map; the model fills in the hard boxes.” It rests on exactly three primitives:

1 · State

the shared record

One typed object every node reads and updates — e.g. {diff, comments, approved, iteration}. When a node returns an update, LangGraph merges it into state (a “reducer” decides how — replace a field, or append to a list like the message history). It's the single source of truth threaded through the whole run.

2 · Nodes

the steps

A node is just a function: state → partial update. A node can be an LLM agent turn, a tool call, or a plain router — and a node can even be an entire sub-agent (a subgraph). You write the boxes; each does one job and hands the state on.

3 · Edges

the wiring

A normal edge A→B always runs B after A. A conditional edge runs a tiny routing function that reads the state and returns the name of the next node — that's how you branch and, by pointing back at an earlier node, loop. Two sentinels bookend it: START and END.

example · walking the graph START→planner writes subtasks into state. planner→coder implements them, writing a diff. coder→reviewer reads the diff and writes approved:false + comments. The reviewer's conditional edge reads approved: it's false → route back to coder (which now sees the comments in state). Next round the reviewer sets approved:true → route to END. Nobody scripted “two rounds” — the loop count fell out of the state.
the actual superpower · checkpointing

Why it's “durable / resumable”

Compile the graph with a checkpointer (in-memory, SQLite, or Postgres) and LangGraph saves the whole State after every node, tagged to a thread id. That one thing buys four properties a free-form loop can't reliably give you:

pause & resume

stop mid-run, come back hours later on the same thread, and it continues from the exact saved state.

human-in-the-loop

interrupt before a risky node, wait for a person to approve or edit the state, then continue.

retry / replay

a node crashed? re-run from the last good checkpoint — not from the very start.

time-travel

rewind to an earlier checkpoint and branch a different path from there for debugging.

A free-form agent loop keeps all of this in one volatile context window — kill the process and it's gone.

The three multi-agent shapes on top of the graph

Once you have nodes + state + edges, wiring several agents together is just choosing how control moves between them:

◉
Supervisorone router/LLM node decides which specialist runs next; each specialist reports back to it. Central brain, clear termination.
⇄
Networkpeers hand off directly to each other — any agent can route to any other (a “handoff”/Command). Flexible, less centralized.
⊞
Hierarchicalteams of agents, each team its own subgraph, with a top supervisor over the team-supervisors. Scales to many agents.

Why it matters — and the Guardian tie-in: LangGraph is a concrete way to build the workflow half of a persistent agent — the durable, checkpointed skeleton that drives the Guardian's repeated cycles and persists memory between them (each run is a thread; state survives), while one node inside a cycle can be the autonomous investigation loop. Explicit graph + checkpointed state = the deterministic routing, pause/resume, and retry an unstructured loop can't reliably provide.

Part IV · The payoff

Loop vs. workflow

The single most useful distinction — both Anthropic and LangGraph draw it in nearly identical words. A naming trap: Anthropic says “agent” for what your intuition calls the autonomous loop.

◍ LOOP (autonomous “agent”)

the model decides the next action each step. Handles novelty; adapts to what it finds. But less predictable, harder to bound in cost, harder to reproduce.

▤ WORKFLOW (orchestrated)

code orchestrates the steps through predefined paths; the model fills specific slots. Deterministic, debuggable, cost-bounded — but rigid.

When to use which: Anthropic's rule — “find the simplest solution possible, add complexity only when needed.” If you can draw the flowchart, write the flowchart (workflow). When steps can't be predetermined, use a loop. The mistake at each extreme: wrapping a fixed 3-step pipeline in an autonomous agent (paying for unused autonomy, losing reproducibility), or scripting an open-ended investigation as rigid branches (it shatters the first time reality doesn't match).

How they compose

Not either/or. The robust pattern is a deterministic outer workflow that invokes an autonomous inner loop at specific steps. The workflow supplies the skeleton — sequence, persistence, gates, retries, cost ceiling. The loop supplies open-ended reasoning at the one step that genuinely needs it. A workflow node can be an entire agent loop.

WORKFLOW — code · deterministic · reproducible
setup load memory from last cycle
per commit prepare context = diff + relevant memory
LOOP — model-driven · open-ended · the one autonomous slot

investigate the risk: grep → read → run test → trace, until a conclusion or the budget cap.

gate validate the finding against a schema
persist update + write memory
emit cycle report
memory is read at prepare, written at persist — knowledge compounds across cycles

The dangerous part (novel investigation) is autonomous; everything that must be dependable (memory, bounds, structure, reproducibility) is plain code. This is visible in Anthropic's own patterns — orchestrator-workers and evaluator-optimizer are workflows whose slots contain dynamic behavior.

The soul of the persistent-memory project
why loop + workflow is the whole design

A guardian is a workflow-driven sequence of memory-carrying autonomous loops.

a pure LOOP can't be a guardian

an autonomous loop has no existence between invocations — no “last cycle,” no bounded cost across a long horizon, no reproducibility. Left on git history it would wander, re-derive, and drift. Autonomy without a harness has no memory and no spine across time.

a pure WORKFLOW can't either

a fixed pipeline marches through commits cheaply — but the instant a diff introduces a risk your branches didn't enumerate, it can't investigate. Structure without autonomy is blind to novelty.

Only the composition works. The workflow is why the agent still exists next week and remembers this week — it drives the repeated cycles, persists memory between them, bounds cost, and keeps runs reproducible. The loop inside each cycle is why it can catch a bug it was never told to look for. The workflow carries the agent through time; the loop makes it intelligent within each moment.
